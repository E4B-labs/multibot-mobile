1. CZYM JEST MULTIBOT
======================

MultiBot = prywatny, self-hosted fork OpenMausBot (MIT) z wbudowanym
Hermes Agent runtime. Produktowa nazwa to MultiBot. Nazwy `openmausbot` i
`.openmausbot` zostają tylko dla kompatybilności migracji starych profili.

Produkt łączy:
- flotę nazwanych botów;
- wybór provider + model per bot;
- Claude Code, Codex, Grok, Gemini, Kimi Code, Qwen Code;
- custom/local model przez base URL + model id + klucz;
- pamięć faktów, graf, markdown i retrieval;
- Skills i teach-a-task;
- Routines cron/manual/webhook;
- bot-to-bot oraz grupy botów;
- komputer przeglądarkowy per bot oraz Shared browser;
- MCP, Composio, plugins i approval policy;
- PWA na telefonie i desktopie;
- authenticated remote access przez jeden port;
- instalatory Windows/Linux/Docker/Termux;
- język polski/angielski.

Hermes/engine jest wspólną warstwą wykonawczą pod providerami, nie osobnym
vendorem widocznym w pickerze. Wewnętrzny string `driverKind: "slafy"` może
istnieć w kodzie, ale nie powinien być pokazywany użytkownikowi jako marka.


2. RUNTIME — TRZY WARSTWY
=========================

Procesy developerskie:

1) React/Vite UI
   pnpm dev
   http://127.0.0.1:5199
   Kod: src/

2) Node/TypeScript harness
   pnpm dev:server
   http://127.0.0.1:8799
   Kod: server/
   Publiczna granica HTTP, auth, provider registry, transcript, grupy,
   routines, workspace, local agent bridge, proxy do engine.

3) Python FastAPI agent engine
   pnpm dev:engine
   http://127.0.0.1:8700
   Kod: engine/
   Zawsze loopback. Harness jest jedynym wejściem sieciowym.

Przepływ zwykłej tury:

UI ChatView
  -> POST /api/bots/:id/messages lub stream/SSE/WS
  -> server/index.ts: startTurn
  -> auth + turn-policy + workspace context
  -> Store transcript/resume cursor
  -> ProviderRegistry wybiera driver
  -> Claude/Codex/ACP albo local/slafy adapter
  -> dla engine: server/engine/proxy.ts
  -> FastAPI app.py
  -> gateway.py (Hermes runtime)
  -> bot profile, identity, memory, skills, tools
  -> provider backend / custom endpoint
  -> event stream przez EventBus
  -> Store + UI transcript.

Ważne: `ENGINE_URL` może wskazywać tylko 127.0.0.1/localhost/::1. Harness
nie wystawia engine na 0.0.0.0.

7. PROVIDERS / MODEL SEMANTICS
=============================

Built-in visible fleet (current intended): Claude, Codex, Grok, Gemini, Kimi,
Qwen, local/custom instances and computer helper. Exact availability depends
on installed/enabled CLI and login state.

Custom model:
- saved in cfg.instances under named id;
- fields: displayName, environment key, model.default, model.baseUrl;
- picker sees named model after save;
- key is never returned by API;
- engine receives provider=custom, base_url and model.

Hermes-style chat command:
- `/model` lists catalog/current selection;
- `/model <provider>/<model>` selects pair;
- `/model <model> --provider <provider>` alternate form.

Reasoning:
- UI supports reasoning control where provider/model supports it;
- value is mapped by driver, not exposed as unrelated provider.

Claude/Codex login:
- login commands execute in provider-specific terminal/modal flow;
- Claude uses official `claude auth login` path;
- Codex uses official `codex login --device-auth` metadata;
- subscription credentials stay with CLI, never in MultiBot config/API.


8. AGENT POWERS / POLICY
========================

Policy modes:
1. Read Only — read current workspace; edits/internet need approval.
2. Ask for approval — read/edit workspace and commands; outside workspace or
   internet need approval.
3. Approve for me — ask only potentially unsafe actions.
4. Full Access — broad access subject to OS/container boundaries.

Agent can, when policy allows:
- read/write files;
- run terminal commands;
- inspect device;
- add/update agents;
- add/update/delete skills;
- create/update/run/delete routines;
- read/write memory;
- create/delete groups and send group messages;
- list/ask other bots;
- use computer/browser;
- use integrations.

Full Access does not bypass Android proot, OS permissions, provider login,
browser availability, or network boundaries. Dangerous operations still need
normal operating-system capability.

Bot-to-bot delegation is intended always-on at product level. MCP-capable
providers receive live peer tools. Codex/API fallback uses explicit @bot
delegation and injects peer response. Recursion depth is capped to prevent
loops.


9. GROUPS
=========

Creation: top `+` -> New group -> select bots -> open room.
Groups appear in sidebar as conversation-like rooms. Clicking a bot or another
group switches active conversation. Group context menu supports delete.

Storage:
- harness durable shadow: `~/.openmausbot/groups.json`;
- engine room transport for execution;
- CLI members represented by durable `mb-<threadId>` engine shadow IDs.

Latest fix (commits b5570ef + 5fc8a1c): DELETE no longer fails with 502 when
engine is offline. Harness removes local group first, then tries engine cleanup
best-effort and returns `{ok:true, engineSynced:false}` if engine unavailable.

Known group limit: mixed-provider group turns still use shared engine room
transport/shadows; fully native mixed-provider room execution is future work.


10. ROUTINES
============

Routines are harness-owned and provider-neutral. They use the same startTurn
pipeline as chat, so they can call provider bots. Engine routines also expose
engine-specific webhook behavior.

Agent rule: when user asks to create/change a routine, agent must call local
MultiBot `create_routine` directly. It must not use ToolSearch, `/schedule`,
provider-private memory or cloud scheduling.

Example schedule:
- cron `35 1 * * *` = daily at 01:35;
- prompt: `Napisz do użytkownika: hej kacper!`.

Harness must remain alive for 24/7 execution. UI can be closed.


11. COMPUTER / TERMUX
=====================

Desktop platforms:
- Playwright browser profile per bot;
- Shared browser profile for all bots;
- live preview and takeover over authenticated WS;
- shared profile has explicit busy/serialization behavior.

Android/Termux:
- Android cannot run normal desktop Playwright bundled Chromium;
- installer uses headless Chromium/CDP path where available;
- PWA can view/control browser remotely;
- no Android desktop browser window unless Termux:X11 is installed;
- chat, memory, skills and routines still work.

Do not “fix” secure-context restrictions by weakening checks. PWA install and
microphone need localhost or HTTPS. Plain LAN HTTP can serve chat but browser
security disables service worker/microphone.


12. AUTH / REMOTE ACCESS
========================

- Harness HTTP API requires `Authorization: Bearer <token>`.
- Both WebSocket upgrade paths are authenticated.
- Engine remains on 127.0.0.1.
- Remote harness serves built `dist/` from same origin/port.
- Static login shell and `/api/health` are public.
- First unauthenticated API request returns 401.
- Token generated at first start, stored in config.json, shown once/logged
  carefully; rotation invalidates old token and active sessions.
- PWA stores token in localStorage and handles global 401.

Recommended remote path:
  tailscale serve --bg --yes http://127.0.0.1:8799

Never bind engine to 0.0.0.0. Never expose harness without auth.


13. ONBOARDING / INSTALLATION
=============================

Onboarding intended sequence:
0. device scan: hostname/platform/arch/RAM/Python/Docker/engine state;
   asks whether to install always-on server;
1. nick + e-mail;
2. detect and optionally install CLI;
3. optional custom model/profile import;
4. permissions (Electron where applicable).

Provision jobs are idempotent per step and expose live SSE progress. CLI
install commands are fixed metadata, shell=false, no silent elevation.

Windows:
  pnpm install:server:windows
Per-user Task Scheduler startup, no UAC, packaged `--server-only` path.

Linux/VPS:
  bash scripts/install-linux.sh
  bash scripts/install-linux.sh --mode docker
  bash scripts/install-linux.sh --dry-run

Android/Termux:
  bash scripts/install-termux.sh
  bash scripts/install-termux.sh --dry-run
Uses termux-services and Termux:Boot.

Development setup requires Node 24+, pnpm, Python 3.12, engine venv and
Hermes editable install at pinned SHA. Playwright browser downloads must use
D:\tmp or another non-C: path on Windows.

18. KNOWN LIMITS / NEXT WORK
============================

Known intentional limits:
- native app-store Android/iOS binaries are not included; PWA is used;
- arbitrary MCP OAuth is not included;
- CLI memory/routines/skills are harness/workspace features, not provider
  private features;
- mixed-driver group turns use engine shadows, not fully native provider room;
- Termux has no desktop Playwright browser window;
- Windows installer unsigned and SmartScreen may warn;
- automatic Windows updates and upstream publisher metadata are not fixed;
- native persistent group transcript semantics remain limited;
- engine/Hermes may fail with exit 78 if profile/runtime/config is wrong;
- secure context is browser policy, not bypassed by MultiBot.

Recommended next checks for new AI:
1. Read GOAL.md, MULTIBOT.md, docs/FEATURES.md, README.md.
2. Run `git status`, `git log --oneline -20`.
3. Run `pnpm typecheck`, targeted tests, then full test/build before changes.
4. Test group delete while engine is stopped and started.
5. Check phone health and service status via SSH port 8022.
6. Never put token/API keys in repo, logs, issue text or this file.
7. Use branches/PRs for teammate work; keep main releasable.
